# AHAVA transport migration: mutual TLS and exact peer pins

This document describes **candidate source in the review branch**, not a deployed change to the F110, Motorola or ACT-Omega.

## Boundary and compatibility
- Local AHAVA plaintext HTTP remains permitted on **loopback only**.
- Remote transport now requires HTTPS with **TLS 1.3**, a private owner-supplied CA, a local client identity and key, and an exact SHA-256 pin on the remote leaf certificate.
- The remote AHAVA server must also present a TLS certificate, validate its client chain, and enforce an exact client leaf-certificate pin. The existing bearer secret is an additional scoped gate, never a replacement for mTLS.
- Address patterns such as 100.64.0.0/10, LAN IPs, or an overlay routing claim **do not** by themselves establish transport identity or permission.
- No connection is opened or key generated by importing the transport-policy module. No ACT endpoint is configured or admitted.

## Owner-private configuration inputs
On the authorized client, set `AHAVA_PEER_URL=https://<approved-peer-host>:43824` and point `AHAVA_TLS_CA_FILE`, `AHAVA_TLS_CERT_FILE`, `AHAVA_TLS_KEY_FILE` to locally protected absolute PEM file paths. Set `AHAVA_TLS_PEER_CERT_SHA256` to the lowercase SHA-256 of the peer leaf DER certificate.

On the authorized server, set an explicitly approved nonloopback `AHAVA_BIND`, `AHAVA_TLS_CERT_FILE`, `AHAVA_TLS_KEY_FILE`, and `AHAVA_TLS_CLIENT_CA_FILE`. Set `AHAVA_TLS_CLIENT_CERT_SHA256` to the expected client leaf DER SHA-256.

Certificate pins can be compared independently using `openssl x509 -in <PUBLIC_CERT> -outform DER | sha256sum`. No CA private key, node signing key, macaroon root, device address or bearer secret belongs in GitHub. Certificate hostnames/IP SANs, validity, CA chain, ownership, revocation and certificate rekeying must be validated before live remote rollout.

## Verification and staged rollout
```sh
node --test tests/test_ahava_transport_policy.cjs tests/test_ahava_mtls_loopback.cjs tests/test_ahava_resume.cjs
```
The unit suite includes wrong pins, remote plaintext refusal, credential file permissions, protected loopback, encrypted resumable content and explicit Android hard-link fixture limitations. The mTLS integration test uses disposable synthetic keys, opens only a short-lived loopback listener and rejects a mismatched server pin.

Before changing the **installed** AHAVA service, record current source and state digests, independently issue and pin each certificate, check thermal admission, run two-way physical transfers with both phones, test revocation/replay/expired certs, and preserve the existing rollback procedure. The ACT-owned peer requires its own separate owner approval and hardware review.

## Health metadata boundary

For remote mTLS connections, even the `/health` response requires a successfully CA-authorized **and exactly pinned** client certificate. It does not export the node label to an arbitrary certificate holder. Existing loopback-only health behavior is preserved for local supervisors. The validation is a source and isolated TLS test, not a claim that every historical AHAVA installation has been migrated.
